## 6. Reusable rights questionnaire

Every response or proposal must answer each item as `YES`, `NO`, `CONDITIONAL`,
or `NOT ADDRESSED`, with the supporting clause/document recorded.

| Topic | Required question/evidence |
|---|---|
| Commercial display | May the mark be displayed in a public commercial product? |
| Website/app | Which web domains, native apps, platforms, and environments are covered? |
| Advertising | May the mark appear on pages carrying general advertising? What separation is required? |
| Subscription | May it appear in free and paid product areas? |
| Remote display | Is display from the provider/rightsholder URL expressly allowed? |
| Hotlink | Is hotlinking permitted, and are referrer/domain restrictions imposed? |
| Cache | Is caching allowed, for how long, and with what refresh policy? |
| Storage | May FutScout retain a copy? In which regions and for how long? |
| CDN | May FutScout or its hosting provider serve a copy from its own CDN? |
| Resizing | Is proportional resizing allowed? Are crop, recolour, conversion, animation, or compression restricted? |
| Format conversion | May PNG/SVG/WebP or other technical conversion occur? |
| Territory | Which countries are covered? Is global internet availability allowed? |
| Term | Effective date, expiry, renewal, suspension, and survival terms. |
| Attribution | Exact credit, copyright/trade-mark notice, link, and placement. |
| Disclaimer | Exact non-affiliation or ownership notice, if required. |
| Removal | Notice method, takedown deadline, cache purge, deletion, and proof obligations. |
| Sublicensing | Can the provider grant the rights, and can hosting/CDN processors receive the necessary limited sublicense? |
| Club marks | Are individual club crests covered? List competitions/clubs and exclusions. |
| League marks | Are competition logos covered? List competitions and versions. |
| Monetization/fees | Advertising, subscription, traffic, impressions, price, overages, and audit rights. |
| Updates | Approved source, versioning, replacement, withdrawal, and obsolete artwork. |
| Evidence | Contract, Order Form, licence, official email, brand guidelines, and signatory authority. |

## 8. Evidence required for each `rightsStatus`

Technical availability, a public URL, an API subscription, generic permission
to use an API commercially, or a disclaimer is never sufficient on its own.

### Keep `REVIEW_REQUIRED`

Keep this status when any material point is missing or ambiguous, including
authority over the underlying mark, commercial use, advertising/subscription,
territory, delivery method, storage, duration, or removal duties.

### `REVIEW_REQUIRED` → `REMOTE_ONLY`

Requires traceable written evidence from the rightsholder or a party that
expressly warrants authority to license the mark. The evidence must identify
the covered assets/entities and expressly permit the actual public commercial
display, relevant monetization, territories, term, and remote/hotlink delivery.
It must also define attribution, withdrawal, and removal. A provider support
reply about URL access is insufficient unless it also establishes the
underlying rights or is paired with rightsholder permission.

### `REVIEW_REQUIRED` → `CACHE_ALLOWED`

Requires everything necessary for `REMOTE_ONLY`, plus express permission for
the exact caching/storage operation: retention, refresh, own hosting/CDN,
technical formats/resizing, processors/subcontractors, deletion, and
post-termination purge. The evidence must say whether the cached copy may be
publicly served; permission merely to reduce API requests is insufficient.

### `REVIEW_REQUIRED` → `APPROVED`

Requires a signed contract, Order Form, licence, unequivocal official email
from an authorized rightsholder/licensor, or equivalent document that covers
the exact production use. It must identify assets, rights granted, commercial
model, surfaces, territories, term, transformations, delivery/storage modes,
attribution, brand guidelines, sublicense/processor needs, updates, and
removal. The approver's authority and the document version must be retained.
`APPROVED` is asset- and scope-specific, never a provider-wide inference.

### `BLOCKED`

Use when permission is refused, the provider/rightsholder lacks authority, the
proposed use is prohibited, mandatory conditions cannot be met, evidence
expires or is revoked, or the source/delivery terms are incompatible. A later
change requires new evidence and a fresh review; it must not be bypassed by an
operational flag.
